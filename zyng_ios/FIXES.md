# Разбор: что было сломано и что исправлено

Проверены все три файла целиком. Ниже — только настоящие баги, а не косметика.

---

## ⚠️ Сначала: одна настройка Xcode, которую надо вернуть

**Build Settings → Swift Compiler - Concurrency → Default Actor Isolation → `nonisolated`**

Ты поставил `MainActor`. Именно из-за этого посыпался весь каскад ошибок
«Sending 'completion' risks causing data races»: настройка делает *каждый* тип
main-actor-изолированным, включая `PacketTunnelProvider`.

Это опасно для расширения: `NEPacketTunnelProvider` вызывается системой с фоновых
потоков, и насильная изоляция на главный актор — прямой путь к зависанию и
последующему убийству процесса watchdog'ом.

Новый код ставит `@MainActor` явно там, где он нужен (`VPNController`, `ContentView`),
и не ставит там, где не нужен (расширение). Поэтому настройку надо вернуть в
`nonisolated` для **обоих** таргетов.

## PacketTunnelProvider.swift

### 1. `NSLog` на каждую пачку пакетов — вероятная причина SIGKILL

```swift
// БЫЛО
packetFlow.readPackets { packets, _ in
    if packets.count > 0 {
        NSLog("📦 Zyng: Read \(packets.count) packet(s)")   // ← на каждой итерации
    }
    self.startPacketHandling()
}
```

С маршрутом по умолчанию через туннель идёт **весь** трафик устройства, то есть
этот `NSLog` вызывался непрерывно. `NSLog` синхронный и дорогой, а у packet tunnel
расширения жёсткий лимит по памяти и CPU. Система просто убивала процесс — это и
был `Thread 1: signal SIGKILL`.

**Исправлено:** логирование из цикла чтения убрано полностью.

### 2. `dnsSettings.matchDomains = nil` — DNS вообще не шёл в туннель

`nil` означает «оставить резолвинг системе». Документированный способ перехватить
все домены — `[""]`.

**Исправлено:** `matchDomains = [""]` (когда включён полный перехват трафика).

### 3. MTU 1500 — без запаса на инкапсуляцию

1500 — это MTU физического интерфейса. Туннель добавляет свои заголовки, поэтому
пакеты фрагментировались бы.

**Исправлено:** `settings.mtu = 1400`.

### 4. IPv6 с маршрутом по умолчанию блокировал весь IPv6

Адрес `fc00::2` + `NEIPv6Route.default()` без реального транспорта = чёрная дыра
для всего IPv6-трафика.

**Исправлено:** IPv6 не настраивается, пока нет транспорта.

### 5. Гонка на `isRunning`

Свойство писалось из `stopTunnel` и читалось из цикла чтения пакетов — разные потоки.

**Исправлено:** доступ через `NSLock`.

### 6. Главное, честно: транспорта нет — пакеты выбрасываются

Туннель поднимается, пакеты читаются и **никуда не отправляются**. С маршрутом по
умолчанию это значит, что при «подключении» устройство теряет интернет целиком.
Приложение выглядит сломанным, и в таком виде оно не пройдёт ревью App Store.

**Исправлено:** добавлен флаг `routesAllTraffic`, по умолчанию `false`. Туннель
поднимается на узком маршруте — можно проверить, что расширение грузится и живёт,
не теряя связь. После интеграции libXray флаг переключается в `true`.

## VPNController.swift

### 7. Гонка при удалении конфигурации — вероятная причина «permission denied»

```swift
// БЫЛО
for mgr in managers ?? [] {
    mgr.removeFromPreferences()   // ← асинхронный, завершения никто не ждёт
}
let m = NETunnelProviderManager()
// ...
m.saveToPreferences { ... }       // ← пишем, пока удаление ещё идёт
```

`removeFromPreferences` асинхронный. Код удалял профили, не дожидаясь результата,
и тут же сохранял новый — гонка с системной базой настроек VPN. Отсюда и
`NEVPNErrorConfigurationInvalid`, и «permission denied», с которыми ты боролся.

**Исправлено:** существующая конфигурация **переиспользуется**, а не удаляется и
пересоздаётся. Так делают все рабочие VPN-клиенты.

### 8. Ошибка загрузки молча проглатывалась

```swift
NETunnelProviderManager.loadAllFromPreferences { [weak self] managers, _ in
//                                                                  ↑ ошибка выброшена
```

Если загрузка падала с «permission denied», код продолжал работать и падал позже
в другом месте — с бесполезным сообщением.

**Исправлено:** ошибка логируется и показывается пользователю.

### 9. `nonisolated(unsafe)` вместо решения

`nonisolated(unsafe) let handler = completion` — это заглушка компилятора, а не
исправление. Она отключает проверку там, где гонка реальна.

**Исправлено:** весь класс переведён на async/await-варианты NetworkExtension API.
Теперь всё выполняется на main actor, `NETunnelProviderManager` (не Sendable)
вообще не пересекает границу изоляции — ошибок конкурентности нет по построению,
без обходных путей.

### 10. Успех сообщался раньше времени

`startVPNTunnel()` не бросил ошибку — это значит «запрос принят», а не «подключено».
UI показывал «Защищено», пока туннель ещё поднимался.

**Исправлено:** состояние UI ведётся от `NEVPNStatus`, а не от результата вызова.

### 11. Учитывался только статус `.connected`

`.connecting`, `.reasserting`, `.disconnecting` схлопывались в «отключено» — UI мигал.

**Исправлено:** публикуется полный `NEVPNStatus`.

### 12. Наблюдатель уведомлений не снимался, синглтон не был защищён

Не было `deinit` с `removeObserver`, а `override init()` был публичным — можно было
создать второй экземпляр контроллера в обход `shared`.

**Исправлено:** добавлен `deinit`, `init` стал `private`.

### 13. Коды ошибок не расшифровывались

**Исправлено:** `NEVPNError.Code` переводится в понятный текст — сразу видно,
проблема в entitlements, в Bundle ID или в самой конфигурации.

## ContentView.swift

### 14. Состояние UI рассинхронизировалось с реальностью

Было два независимых источника правды: локальный `@State var state` и
`vpnController.isConnected`. Если VPN отваливался сам, `state` оставался `.on` —
приложение показывало «Защищено» при отключённом VPN.

**Исправлено:** `state` вычисляется из `vpn.status`, локального флага больше нет.

### 15. `onChange` не запускал таймер

```swift
.onChange(of: vpnController.isConnected) { _, connected in
    if connected && state == .connecting {
        state = .on          // ← startTimer() не вызывается
    }
}
```

Если подключение завершалось через уведомление статуса, а не через колбэк, таймер
не стартовал вообще.

**Исправлено:** и статус, и время идут из одного обработчика.

### 16. Таймер никогда не останавливался и врал после сворачивания

`Timer.scheduledTimer` не инвалидировался при исчезновении view (утечка), а счётчик
`elapsed += 1` замирал, пока приложение в фоне — время показывалось неверно.

**Исправлено:** время считается от `connectedAt` (`Date`) через
`Timer.publish` + `.onReceive`. Утечки нет, после фона время корректное.

### 17. Ошибка не сбрасывалась

`vpnError` выставлялся и оставался на экране навсегда, даже после успешного подключения.

**Исправлено:** ошибка живёт в `VPNController.errorMessage` и сбрасывается при `.connected`.

### 18. Выбранный сервер не переживал перезапуск

`save()` сохранял только список серверов. `Server.id` — это `UUID()`, который
генерируется заново при каждом парсинге, поэтому `load()` всегда сбрасывал выбор
на первый сервер.

**Исправлено:** выбор сохраняется по строке ключа (`zyng_selected`).

### 19. `@StateObject` для синглтона

`@StateObject` предназначен для объектов, которыми view владеет. Для `.shared`
правильный аргумент — `@ObservedObject`.

**Исправлено.**

### 20. Удаление выбранного сервера оставляло выбор пустым

`selectedID = nil` — после удаления не выбирался следующий сервер.

**Исправлено:** выбирается первый оставшийся.

## Что делать дальше

1. Верни **Default Actor Isolation → `nonisolated`** для обоих таргетов.
2. Замени три файла на новые версии.
3. `⌘⇧K` → `⌘B`.
4. Запусти на устройстве, смотри Console.app с фильтром «Zyng». Ожидаемые логи:
   ```
   🔵 Zyng: startTunnel
   ✅ Zyng: ключ получен (N симв.)
   ✅ Zyng: сетевые настройки туннеля применены
   🔵 Zyng: VPN status = connected
   ```
   Логов о пакетах теперь нет — и не должно быть.
5. Если расширение живёт и не убивается — переходи к интеграции libXray
   (`LIBXRAY_INTEGRATION.md`), затем переключай `routesAllTraffic` в `true`.

**Честно про статус:** после этих правок приложение перестанет падать и врать в UI,
но полноценным VPN оно ещё не станет — за туннелем нет транспорта. Это следующий шаг,
и он самый большой.
